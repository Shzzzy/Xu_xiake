# 徐霞客旅行规划：业务需求与流程

> 文档基线：`codex/ai-butler-guidebook`，提交 `698ebcf`，整理日期 2026-09-27。  
> 本文描述“当前代码真实行为”，不代表历史设计稿中的未来能力。

## 1. 产品定位

徐霞客旅行规划是一个中文旅行管家应用。用户给出旅行条件后，系统负责：

1. 判断路线、交通方式和时间是否可行。
2. 在预算、人数、天数、每日时间窗和节奏约束内安排行程。
3. 用高德提供路线、地点、坐标和地图事实。
4. 用 DeepSeek 做候选景点选择、排序、每日文案和历史背景说明。
5. 用 Tavily 补充非自驾交通价格和景点门票资料。
6. 输出可逐页预览的路书，并允许用户在浏览器中打印为 PDF。

核心原则是“事实、算术和文案分工”，而不是把整份行程交给单一大模型自由生成。

## 2. 目标用户与典型场景

- 已确定目的地，希望围绕目的地安排 1–16 天详细行程的用户。
- 只有出发地和偏好，需要系统先推荐目的地的用户。
- 有多个途经点，需要判断顺路程度、交通方式和时间是否够用的用户。
- 长途旅行用户，需要系统在“直达、延长天数、减少目的地”之间给出选择。
- 需要把最终行程输出为完整路书的用户。

## 3. 业务范围

### 3.1 当前已实现

- 已知目的地规划。
- 未知目的地九步推荐。
- 出发地、目的地、最多 5 个途经点。
- 单程或往返；往返支持快速返程和回程再玩。
- 每段路线可单独设置交通方式和旅行风格。
- 成人、儿童、总预算、每日出发与结束时间、节奏和兴趣偏好。
- AI 推荐预算。
- Open-Meteo 天气接入。
- 长距离自驾可行性判断和 A/B/C 方案选择。
- 1–16 天详细管家排程。
- 17–365 天长线阶段规划。
- 逐页流式路书预览。
- 浏览器打印导出 PDF。
- 共享动态地点及其稳定 SVG 配图。

### 3.2 当前不是业务主链路

- 用户账号、登录态和跨用户数据隔离不是本旅行规划流程的依赖。
- 行程正文不落库。
- 没有订单、支付、票务库存或真实预订能力。
- 没有 17 天以后的逐日天气预报和逐日详细路书。
- 高德天气 API 已有客户端封装，但业务未调用。

## 4. 用户输入与业务含义

### 4.1 已确定目的地

| 字段 | 业务含义 | 当前约束 |
| --- | --- | --- |
| 出发地 | 路线起点 | 必填 |
| 目的地 | 路线终点 | 必填 |
| 途经地 | 希望停留或经过的地点 | 最多 5 个 |
| 往返 | 是否规划返程 | 单程或往返 |
| 返程模式 | 快速返回或回程再玩 | 往返时生效 |
| 单段交通 | 火车、飞机、自驾、大巴、轮船或通用偏好 | 可逐段覆盖 |
| 旅行风格 | 直达或边走边玩 | 可逐段覆盖 |
| 出发日期 | 行程第一天 | 详细行程一般限制在 16 天预报窗口内 |
| 天数 | 总旅行天数 | 1–365 天；1–16 天走详细规划，17 天以上走长线阶段规划 |
| 每日时间 | 每日出发和最晚结束时间 | 用于扣除交通、住宿、用餐和休息容量 |
| 节奏 | 轻松、适中、深度 | 控制每日景点数量与时间密度 |
| 兴趣 | 自然、人文、美食、摄影等 | 用于候选选择和每日文案 |
| 成人/儿童 | 交通、门票、餐饮和房间计算基础 | 至少 1 位成人；儿童可为 0 |
| 总预算 | 全团预算上限 | 不是必须花完的目标 |
| 自驾能源 | 燃油、纯电或混动 | 仅在存在自驾段时要求 |

### 4.2 未知目的地九步向导

1. 想看的风景类型。
2. 可安排的天数。
3. 每日节奏。
4. 想加入的体验。
5. 出发地。
6. 出发日期。
7. 交通偏好。
8. 单程或往返。
9. 同行人数与预算。

系统会据此推荐目的地，再进入与“已知目的地”相同的管家规划流程。

## 5. 端到端用户流程

### 5.1 已确定目的地流程

```text
入口页
  -> 填写目的地与旅行条件
  -> 可选：点击 AI 推荐预算
  -> 前端校验人数、预算、时间窗和自驾能源
  -> 获取目的地天气
  -> 调用高德准备路线与候选景点
  -> 生成交通门到门时间
  -> 若长途自驾不可行，进入 A/B/C 方案选择
  -> 确定性规划管线
  -> 逐页路书预览
  -> 用户点击生成路书
  -> 浏览器打印窗口另存为 PDF
```

### 5.2 未知目的地流程

```text
入口页
  -> 九步向导
  -> 推荐目的地
  -> 回填为已确定目的地表单
  -> 进入同一条行程规划链路
```

### 5.3 可行性方案流程

当长途自驾在真实门到门时间下不可行时，系统不会强行生成一份不可能的行程，而是返回三选一方案：

- 方案 A：长距离段改为直达交通，落地后再游玩。
- 方案 B：延长旅行天数，并按每日驾驶上限拆段。
- 方案 C：保留部分重点目的地，减少必须覆盖的途经点。

用户选择后，系统用调整后的路线、天数和交通方式重新进入规划。

### 5.4 路书生成流程

1. 规划结果先转成统一 `TripPlan`。
2. 路书按封面、概览、路线、预算、每日行程、结尾等页面逐页生成。
3. `/api/guidebook-preview` 以 NDJSON 逐页推送。
4. 前端校验 `runId`、连续页码和 checksum。
5. 所有页面到齐后才允许导出。
6. 当前 Netlify 环境没有可用无头浏览器，因此使用浏览器打印，不再在服务端启动 Playwright。

## 6. 核心业务规则

### 6.1 时间规则

- 每日时间窗必须先扣除交通门到门时间。
- 每日安排包含 30 分钟酒店入住/休整容量。
- 景点有真实建议停留时间，时间窗放不下的景点不能静默截断。
- 景点优先于休息；午餐和晚餐按剩余容量动态保留。
- 休息和机动时间累计上限为 90 分钟，剩余时间留白，不再生成超长“必要休息”。
- 交通时间超过每日可用时间时，该日时间轴应失败，不能伪造排程。

### 6.2 交通规则

- 通用交通偏好为经济、均衡、效率时，跨省且距离至少 800 km 默认选择飞机。
- 用户明确选择飞机、火车、自驾、大巴或轮船时，优先尊重用户选择。
- 飞机门到门时间至少按 300 分钟估算。
- 火车门到门时间至少按 180 分钟估算。
- 自驾优先使用高德路线实际时长，并增加每两小时至少 15 分钟休息和至少 30 分钟缓冲。
- 超长自驾按每日驾驶上限拆成执行分段，但预算仍按原始 leg 计算。

### 6.3 预算规则

当前确定性预算口径：

```text
交通 = 单人价格 × 同行人数 × 交通 leg 数
住宿 = 房间数 × 晚数 × 每晚价格
餐饮 = 同行人数 × 天数 × 每人每日餐标
门票 = 成人数 × 成人票价 + 儿童数 × 儿童票价
其他 = max(200, 前四项 × 10%)
总费用 = 交通 + 住宿 + 餐饮 + 门票 + 其他
```

- 自驾价格允许按车辆总价计算，再按同行人数折算用于总预算。
- 当前确定性预算把“房间数”设为同行人数，即每人一间房。
- 预算上限用于判断方案是否超支，不要求刚好花完。
- 价格置信度分为：
  - `verified`：有明确来源。
  - `reference`：检索得到的参考区间。
  - `fallback`：本地公式或最低价兜底。

### 6.3.1 AI 推荐预算

- 基础金额由本地确定性公式计算，DeepSeek 只负责整理解释文案，不能修改金额。
- 默认住宿参考价为 600 元/间/晚。
- 默认餐饮参考价为 150 元/人/天。
- 默认成人门票整趟参考价为 200 元，儿童为 100 元。
- 默认其他费用最低 200 元。
- 简单且数据可信的行程使用 10% 缓冲；普通行程 15%；未知交通价格、长途、多段或 10 天以上复杂行程使用 20% 缓冲。
- 推荐预算向上取整到百元。

当前最终详细规划使用另一组默认值：住宿 500 元/间/晚、餐饮 220 元/人/天、门票兜底 80 元。这会导致“AI 推荐预算”和最终规划预算采用不同基准，是当前需要统一的高优先级问题。
### 6.4 景点规则

- 高德是候选景点主来源，按热门景点、风景名胜、博物馆、公园、地标等关键词检索。
- DeepSeek 只能从候选 ID 中选择和排序，不能自由发明不存在的景点。
- 景点必须位于当天所在地，避免“已经飞到另一城市，却安排原城市景点”。
- 同一景点不能跨天重复，除非当地候选不足，系统可在同一天内复用。
- 非移动日优先安排真实景点；候选确实不足时才降级为自由休整。
- 途中地点在部分发现链路中可由 Tavily 和 DeepSeek 校核后进入共享地点库；详细管家路径当前以高德候选为主。

### 6.5 天气规则

- 天气是增强信息，不是规划硬前置条件。
- 当前通过 Open-Meteo MCP 获取最多 16 天预报。
- 有坐标时直接按坐标查询，没有坐标时先用地名解析坐标。
- 降水、极端温度和户外占比会影响每日文案、注意事项和雷达图。
- 17 天以上行程只展示前 16 天天气趋势，后续以实际天气为准。

### 6.6 失败与降级规则

- 缺少 `DEEPSEEK_API_KEY`：确定性规划不可用。
- 高德路线或 POI 硬前置失败：交通/候选阶段 fail closed，不生成伪造路书。
- 候选景点不足：停止游玩计划生成，不虚构景点。
- 非自驾交通价格缺失：使用本地最低参考价，并标记为 fallback。
- 门票资料缺失：使用本地参考价或统一票兜底。
- 单日文案失败：只降级当天，改用经校验的本地安全文案并留痕。
- 结尾文案失败：使用确定性结尾文案。
- 任何未通过校验的页面都不能进入正式预览和导出。

## 7. 用户可见结果

- 行程标题、摘要、出发日期、天数、每日时长和候选景区数量。
- 路线节点及每段交通方式和旅行风格。
- 逐日天气。
- 路线与交通页。
- 预算总览、分类预算和每日预算。
- 每日时间轴、景点、餐饮、休息和导航。
- 景点历史背景、注意事项和当地提示。
- 每日雷达图。
- 行程条件未完全满足时的违规提示。
- 路书结尾和旅行寄语。

## 8. 当前验收重点

- 北京到四川、5 人、5 天往返默认飞机，交通费用按 5 人和往返 leg 累加。
- 通勤时间必须从每日容量扣除。
- 非移动日应包含当地真实候选景点，不连续显示自由休整。
- 到开封后不能再安排北京景点；到下一个城市后不能回头安排上一城市景点。
- 路线地图需完整显示起点、途经点和目的地。
- 每日地图应聚焦当天所在地与当天景点，不能总显示整条跨省路线。
- 预算明细之和应等于预计总费用；每日预算之和应等于总预算。
- 路书预览不得有空白页、内置双滚动条或自动跳页。
- 预览和 PDF 必须使用同一份校验后文案和预算数据。

## 9. 当前已知风险与待改进项

- 天气仍经第三方 Open-Meteo MCP 中转；官方 REST 直连尚未落地。
- 高德 `weather()` 已实现但未接入业务，容易造成“以为高德在提供天气”的误判。
- 确定性预算按同行人数计算房间数，legacy 适配器仍有两人一房的旧口径，存在口径不一致风险。
- 详细行程限制 16 天；17–365 天仅做阶段规划，不是完整逐日路书。
- 行程和保存状态主要保存在前端内存与 `localStorage`，不是账号级跨设备数据。
- Supabase 当前作为托管 Postgres 使用；项目代码没有直接使用 Supabase SDK、RLS 或 Supabase Auth。
- `SUPABASE_URL`、`SUPABASE_PUBLISHABLE_KEY`、`SUPABASE_JWKS_URL`、`SUPABASE_DB_PASSWORD` 在当前代码中没有运行时引用，属于保留配置，需避免误认为已接入。
- 生产密钥曾出现在聊天记录中，建议在部署验证完成后统一轮换。
