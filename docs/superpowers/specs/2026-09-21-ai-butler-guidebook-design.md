# AI 管家式路书生成设计

- 日期：2026-09-21
- 状态：设计已确认，待原型确认后实施
- 适用范围：「我知道去哪」与「帮我决定去哪」共用的路书内容生成链路
- 版式原型：`.superpowers/brainstorm/2928444-1789879924/content/`（页序与版式已定稿，本次不改）
- 关联设计：`docs/superpowers/specs/2026-09-20-travel-plan-output-pdf-design.md`（固定结构、降级顺序、历史引用白名单继续有效）

## 1. 背景与问题

当前链路是「两套并行」：

- DeepSeek 输出**标题、一段行程摘要、以及每天想放哪些景点**。
- 本地 `plan-output-adapter` 把这些景点**压平成一条列表**，交给 `travel-schedule` 按「景点规模 + 最佳时段 + 每日容量」**重新分配每天**，时间轴、停留时长、费用也都由本地算。

于是摘要描述的是 AI 心里的分天方案，页面/路书呈现的是本地重排后的结果，两者之间没有任何校验；而且 AI 摘要只出现在结果页头部，**根本进不了路书**，也不会被下游纠正。这就是「摘要与排程对不上」的根因，靠调提示词无法根治。

## 2. 已确认的产品规则

| 项 | 结论 |
| --- | --- |
| 结构 | 路书页序、版式、字段位置固定，由本地模板渲染 |
| 排程 | 由 DeepSeek 当管家，在用户条件内排出完整计划（含时间轴、餐饮、住宿、休息、费用、分析） |
| 数据来源 | 地图与导航用高德，天气用天气 API，**生成路书时取一次**并固化进路书 |
| 违规处理 | 本地做确定性校验 → 带违规清单回喂 DeepSeek 重排，**最多 1 次** |
| 骨架调用上限 | 技术重试与内容重排**共用额度**：骨架最多尝试 3 次 |
| 结尾页 | 不与本次行程强绑定，只要与旅行相关即可 |
| 预算「其他」 | 指杂事开销（中途打车、纪念品、零食、活动道具等），默认按前四类合计 10%、最低 ¥200 预留 |
| 预算推荐 | 表单提供「AI 推荐」按钮，用户点击触发一次 DeepSeek 估算 |

## 3. 非目标

- 不改路书页序、版式、PDF 导出与逐页预览方式。
- 不引入账号、多用户或跨设备保存。
- 不查询真实班次（火车/飞机/轮船仍为估算）。
- 不做无限重试；不允许因为预算压不下去而卡死。
- 不改历史引用的白名单机制与「必须可核验」的规则。

## 4. 职责边界

三层，边界清晰：

1. **条件层（本地）**：出发地、目的地、途经点、日期天数、人数、全团预算、交通偏好、节奏、兴趣、每日起止时间；以及高德算出的路线分段与坐标。
2. **管家层（DeepSeek）**：排程骨架（含标题与摘要）、每日文案、结尾文案。
3. **模板与数据层（本地）**：高德（地图、导航、距离、耗时）、天气 API（逐日天气）、固定模板渲染、逐页预览、按需导出 PDF。

判定职责：**内容是否合规由本地判定**，不由模型自述；模型只负责在约束内重排。

## 5. 生成时序

1. 本地取数据：高德算路线分段与坐标 → 天气 API 取逐日天气。**天气必须排在管家之前**，否则无法按天气安排室内外。
2. 调用 1「骨架」：输入条件 + 路线 + 天气 + Tavily 检索到的候选景点资料，输出排程骨架 + 标题 + 摘要。
3. 本地校验（第 7 节）。有违规 → 带违规清单重排 1 次；重排后再校验一次。
4. 骨架定稿后并行执行：每天一份文案（调用 2…N）、结尾文案（调用 N+1）；同时本地补齐静态地图、导航链接。
5. 组装 `TripPlan` → 逐页流式渲染 → 用户点击后才渲染 PDF。

## 6. 数据结构与接口

渲染层（模板、逐页预览、PDF）消费的仍是现有 `TripPlan`，本次只改它的**内容来源**。

### 6.1 骨架（调用 1 的输出）

```
title    string
summary  string                     // 与排程同源，不再独立生成
days: [{
  day        number
  theme      string
  nodes: [{
    type      transport | transfer | attraction | meal | rest | hotel | night-activity
    startTime string                  // "08:15"
    endTime   string                  // "09:00"
    name      string
    location? string
    transportMode?   economy | balanced | speed | train | flight | drive | bus | ship
    transportMinutes? number
    stayMinutes?      number
    estimatedCost     number
    tips?             string
  }]
  radar: { physical, childFit, weatherSensitivity, timeCost, crowding }   // 0–100
}]
```

本地补齐模型不该产出的字段：`date`（按出发日期顺序）、`weather`（天气 API）、`mapUrl / navigationUrl / qrCodeUrl`（高德）。**导航链接一律由本地生成，模型不写 URL。**

### 6.2 每日文案（调用 2…N 的输出）

```
day        number
purpose    string
highlights string[3–5]              // 每条「标题：说明」
cautions   string[2–5]
history: [{ title, background, source }]   // 必须带来源
```

给不出来源的条目直接丢弃；沿用在路书中展示「计划中未记录可核验的历史沿革」的降级文案。

### 6.3 结尾（调用 N+1）

复用现有 `TripClosing { quote, source, message }`：`quote` 从既有白名单选择，选不到留空；`message` 允许泛化。

### 6.4 输入契约

条件 + 高德路线与坐标 + 逐日天气 + Tavily 检索结果（地点来源保持可追溯）。模型只能在给定候选资料内挑选景点。

## 7. 校验规则与重排契约

### 7.1 确定性规则（本地纯函数，零网络零 AI）

| 代号 | 判定 |
| --- | --- |
| `TIME_WINDOW` | 每个节点在用户填写的每日起止时间窗内；时间格式合法、单调不重叠 |
| `DAY_COVERAGE` | 天数等于用户设定，序号 1…N 连续；每天至少一个非休息类节点 |
| `MISSING_SLOT` | 每天必须有用餐、住宿、收尾休息节点；夜游可选 |
| `OVER_BUDGET` | 全部节点费用之和 ≤ 全团总预算 |
| `OVER_CAPACITY` | 当天景点停留时长合计 ≤ 当日可用时长（时间窗 − 用餐 − 休息 − 交通） |
| `PACE_EXCEEDED` | 每天核心景点额度不超过节奏上限（轻松 2 / 适中 3 / 充实 4） |
| `UNKNOWN_PLACE` | 骨架中的景点必须来自输入候选（Tavily 结果、用户途经点/目的地、灵感库） |
| `TRANSPORT_CONFLICT` | 用户明确指定交通方式时，不得出现冲突节点 |

### 7.2 违规清单契约

```
{ code, day?, nodeIndex?, message, detail: { expected, actual } }
```

`message` 用中文写清楚，用户也读得懂；`detail` 给模型看差值。

### 7.3 重排契约

- 回喂内容 = 原骨架 + 违规清单 + 同一份输入。
- 提示词硬约束：**只改被判定违规处**，其余保持原样；**不得引入清单外景点**。
- 预算超支按既有降级顺序处理：住宿档次 → 付费景点或体验 → 餐饮标准 → 交通方案 → 低优先级途经点。
- 重排后再跑一次同一套校验；仍不合规则**不再重排**，交付「带提醒的可用版本」。

## 8. 失败与降级

任何单点失败都不得让整份路书缺失，且**每次降级都要在固定槽位留痕**。

| 失败点 | 处理 | 可见痕迹 |
| --- | --- | --- |
| 天气 API | Open-Meteo → 高德天气 → 都失败则隐藏天气区块 | 总览页天气区消失 |
| 高德路线 | 用模型估算距离与耗时 | 数据来源页标注「距离与耗时为估算」 |
| 静态地图 | 保留导航链接与时间轴，地图位置给占位图 | 显示「地图暂不可用」 |
| Tavily | 只用灵感库与用户输入作为候选 | 数据来源页标注「本次未做联网检索」 |
| 骨架调用（网络/超时） | 自动重试 1 次 | — |
| 骨架格式非法 | 带更严格格式指令重试 1 次 | — |
| 骨架彻底失败 | 退回本地 `travel-schedule` 排基础行程 | 提示条：「本次为兜底行程，未使用 AI 规划」 |
| 重排后仍不合规 | 交付带提醒版本 | 提示条 + 当日执行提醒逐条列出 |
| 某天文案失败 | 该天用本地默认文案 | 该页标注「本页分析未能生成」 |
| 结尾失败 | 确定性兜底文案 | 数据来源页标注「结束语使用现代语言释义」 |
| 整体超时 | 渲染已完成页面，其余用兜底 | 顶部提示条说明未完成部分 |

## 9. 调用预算与成本上限

- 骨架：**最多尝试 3 次**（正常 1 + 技术重试 1 + 内容重排 1，共用额度）。
- 每日文案：N 次，**并行**，每次 ≤ 1200 tokens。
- 结尾：1 次，≤ 800 tokens。
- 骨架单次 ≤ 4000 tokens。
- 2 天行程：正常 4 次调用（其中 3 次并行），最坏 6 次。

## 10. 一并实施的相关改动（预算）

1. 结果页预算侧栏与路书预算页：把「其他」改为「其他 · 杂事开销」，并补一行说明（中途打车、纪念品、零食、活动道具等零散支出）。
2. 修正「其他」恒为 ¥0：兜底路径不再显式传 0，改为默认按前四类合计 10%、最低 ¥200。
3. 表单「全团总预算」旁新增「AI 推荐」按钮：用户点击后按目的地、天数、人数、交通偏好请求一次 DeepSeek，返回建议总额与分类（交通/住宿/餐饮/门票/杂事），一键填入预算并展示分类提示。**仅在用户点击时调用一次。**

## 11. 新增视觉元素（需原型确认）

1. 「未满足约束」提示条：结果页顶部、路书总览页、每日执行提醒。
2. 预算「其他 · 杂事开销」说明。
3. 数据来源页措辞更新：明确「地图与天气按需取一次」「行程编排由 DeepSeek 完成」。

这三处属于固定槽位内的新增内容，**不改变页序与版式骨架**；原型确认通过后才开始写代码。

## 12. 测试与验收

### 12.1 单元测试

- 校验器：8 条规则各配正反用例，断言违规清单的 `code` 与 `detail`。
- 骨架解析：缺字段、越界值、非法类型被拒；多余字段丢弃。
- 文案解析：条数约束；无来源的历史条目被丢弃。
- 重排提示词构造：违规清单完整带入，且包含两条硬指令。
- 组装器：骨架 + 文案 + 数据 → `TripPlan` 字段映射正确。

### 12.2 契约测试（假响应）

- 正常路径：页数恒等于 `4 + 2N + 3`。
- 违规路径：恰好 1 次重排；第二次合规后无提示条。
- 仍不合规：不再发起第二次内容重排，提示条列出违规项。
- 技术失败：骨架失败重试 1 次；再失败走兜底。
- 额度：骨架总尝试 ≤ 3。

### 12.3 一致性测试

- 摘要中提到的景点名必须能在 `days` 的景点里找到（按名称子串匹配），且 `days` 中的每个景点名也必须在摘要中出现一次；任何一侧多出或缺失即失败。
- 直接调用校验器，断言生成产物零违规。
- 费用汇总 ≤ 全团总预算。

### 12.4 端到端（浏览器，真实链路）

- 现有 task-6 用例：向导 → 生成 → 逐页路书 → 导出按钮可用 → 移动端无溢出 → 控制台无报错。
- 新增：摘要中的景点名必须能在对应那一天的页面找到。
- 新增：出现提示条时，对应违规项必须同时出现在当天执行提醒里。

### 12.5 验收标准

1. 页序与页数不变（`4 + 2 页/天 + 3`）。
2. 一次正常生成校验器全绿。
3. 摘要与每日排程逐项一致。
4. 用户条件（时间窗/预算/节奏/交通）被遵守；不合规时最多返工 1 次且违规可见。
5. 任何单点失败都不会导致整份路书缺失，且都有可见痕迹。
6. 地图、导航、天气来自对应 API，生成时取一次并固化。
7. 调用次数不超上限（正常 ≤ 4，最坏 ≤ 6）。
8. `npm run typecheck`、`npm test`、`npm run build` 通过；开发与构建产物均无控制台报错、无横向溢出。

## 13. 替换范围与迁移顺序

### 13.1 不动

`guidebook-html.server.ts`（页序与版式）、逐页流式预览、按需 PDF 导出、`amap.server`、天气链路、Tavily 检索与地点校核、灵感库、节奏额度与白名单等既有资产。

### 13.2 改造

| 模块 | 改造后 |
| --- | --- |
| `live-planner.functions.ts` | 变成编排器：骨架 → 校验 → 重排 → 并行文案 → 结尾 |
| `live-planner.ts` | 换成骨架 schema、文案 schema、重排提示词 |
| `plan-output-adapter.ts` | 变成组装器：骨架 + 文案 + 数据 → `TripPlan` |
| `travel-schedule.ts` | 降级为兜底与辅助（仅在骨架失败时使用） |
| `PlannerPrototype.tsx` | 取新链路产物；结果页 UI 不变 |

### 13.3 新增

`plan-validator.ts`（校验器与违规清单类型）、`planner-skeleton.ts`、`planner-day-copy.ts`、`planner-orchestrator.server.ts`。

### 13.4 迁移顺序

1. 原型确认（第 11 节）。
2. 新增纯模块（校验器、schema、解析）与单测；**现有链路不变**。
3. 新增编排器，藏在开关后；开关关闭时行为与今天完全一致。
4. 开发环境打开开关跑通，比对新旧产物结构一致性。
5. 默认切换到新链路，旧链路降级为兜底。
6. 清理与文档更新（涉及删除的条目**单独列清单并经确认后**再执行）。

## 14. 风险与回滚

- 开关保证随时回退到当前行为。
- 建议在服务端记录每次生成的实际调用次数与 token（默认关闭，需显式开启）。
- 已知风险：模型自行排时间轴的自律性（靠校验器 + 1 次返工兜底）；输出变重导致等待变长（靠逐页流式缓解）；天数越多风险越大。

## 15. 已知环境限制

- 本地开发在 Windows 上运行，`npm run preview:restart` 依赖 `/proc`，在 Windows 不可用；构建产物校验改用 `npm run preview`。
- 浏览器自动化点击不会真正落盘 PDF 文件，下载落盘需人工确认。
