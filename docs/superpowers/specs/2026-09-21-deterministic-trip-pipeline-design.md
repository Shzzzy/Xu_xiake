# 确定性旅行规划与分阶段校验设计

## 1. 背景

当前生成的排程与预算存在系统性问题：

- 长途交通选择错误，2000 km 级路线仍可能按驾车计算。
- 交通、住宿和总预算由模型节点费用汇总，未按人数、房间数、往返段数计算。
- 通勤时间没有可靠占用每日容量，时间轴频繁出现“自由活动/自由休整”。
- 候选景点可能为空，模型只能输出泛化活动。
- DeepSeek 一次性产出全部内容后再统一修复，错误会跨阶段传播。

目标是把时间、费用、地点和容量从模型自由生成中收回，由本地确定性规则负责；DeepSeek 只负责受限的景点选择、分析和文案。所有生成步骤分阶段进行，每阶段校验通过后才进入下一步，并逐页推送结果。

## 2. 目标

1. 高德负责路线、坐标、POI、距离和导航。
2. 本地负责交通方式、门到门耗时、每日容量、房间数和预算计算。
3. Tavily 只负责非自驾交通价格与景点门票资料。
4. DeepSeek 只在候选集合内选景点、排序、分析和写文案，不得修改价格、时间或人数。
5. 每个阶段有独立结构、校验器和失败策略；通过后才进入下一阶段。
6. 每日文案逐日生成、逐日校验，路书逐页推送，不等待全部内容完成。

## 3. 非目标

- 不提供实时航班余票、实时票价或官方开放时间保证。
- 不要求高德提供没有的数据，例如航班、火车票价和班次。
- 不把 DeepSeek 当作预算计算器或时间计算器。
- 不为了页面好看虚构景点、票价、时间或历史来源。

## 4. 总体数据流

```text
用户条件
  -> A. 路线归一化（高德）
  -> B. 目的地候选 POI（高德）
  -> C. DeepSeek 景点选择与顺序提案
  -> D. 本地时间轴与容量校验/修复
  -> E. Tavily 价格资料 + DeepSeek 价格归纳
  -> F. 本地预算计算与校验
  -> G. DeepSeek 逐日文案生成
  -> H. 单日文案校验
  -> I. 单页渲染与流式推送
  -> J. 全文/PDF 导出
```

任何阶段未通过校验时，只能修复当前阶段或降级当前阶段，不允许把错误带入后续阶段。

## 5. 分阶段契约

### A. 路线归一化（本地 + 高德）

输入：出发地、目的地、途经点、往返、用户交通偏好、日期、人数。

输出：

```ts
type NormalizedLeg = {
  id: string;
  kind: "outbound" | "return";
  from: string;
  to: string;
  distanceKm: number;
  mode: "flight" | "train" | "drive" | "bus" | "ship" | "walk";
  doorToDoorMinutes: number;
  minimumPerPersonCost: number;
};
```

规则：

- 跨省且单程约 >=800 km 的通用偏好默认飞机。
- 用户明确选择 `drive` 或 `train` 时尊重用户选择。
- 飞机耗时包含机场接驳、值机、安检、飞行、取行李和机场到酒店。
- 自驾按车辆计算；非自驾按单人价格计算后乘以人数。

校验：每个 route leg 必须生成；距离、模式、分钟数和单人最低价不得缺失或为负。

### B. 目的地候选 POI（本地 + 高德）

输入：目的地名称、地区、兴趣、用户节奏。

输出：已去重并过滤非景点类 POI 的候选集合：

```ts
type DestinationCandidate = {
  id: string;
  name: string;
  type: string;
  address: string;
  location: [number, number];
  publicUrl: string;
};
```

规则：

- 排除住宿服务、餐饮服务、购物服务等非景点 POI。
- 目的地名称可能是城市、景区或区域，必须支持精确查询和无城市重试。
- 候选少于所需数量时，不允许继续生成游玩日。

校验：候选名称唯一、坐标有效、公开 URL 不含密钥。

### C. DeepSeek 景点选择与顺序提案

DeepSeek 只能从 B 产生的候选中选择，输出结构化提案：

```ts
type AttractionSelection = {
  day: number;
  candidateId: string;
  sequence: number;
  stayMinutes: number;
  reason: string;
};
```

不包含 URL、价格、预算、酒店或最终时间。

校验：

- `candidateId` 必须在候选集合内。
- 直达模式不得为了景点绕路。
- 边走边玩模式允许沿途和到达后景点。
- 每日景点数量不得超过节奏上限。
- 非移动日必须有候选景点；移动日可按剩余时间安排。

### D. 本地时间轴与容量校验

本地根据路线、距离、营业窗口、交通时间和固定节点生成执行时间轴。

规则：

- 先扣除通勤、换乘、用餐、入住和必要休息，再分配景点。
- 若剩余时间不足完整游览，尝试附近小景点；仍不足则休息。
- 通勤时长必须占用当天容量。
- 时间轴节点不得超出每日窗口或重叠。
- 没有合适景点时显示自由活动，但不得把连续多日全部填成自由活动。

校验失败：仅对当前日重排，最多 1 次，不影响已通过的其他日期。

### E. Tavily 价格资料 + DeepSeek 价格归纳

输入：已确定的交通 leg、已选景点、人数、日期和出行方式。

Tavily 查询：

- 非自驾交通：航班/高铁/火车/大巴/轮渡价格。
- 景点：门票、淡旺季和优惠票。

DeepSeek 只负责把资料整理成结构化区间，不直接生成最终总价。

### F. 本地预算计算与校验

```text
交通 = 单人单程价格 × 人数 × 往返段数
住宿 = 房间数 × 晚数 × 每晚价格
餐饮 = 人数 × 天数 × 每日餐标
门票 = 成人人数 × 成人票价 + 儿童人数 × 优惠票价
其他 = max(200, 前四项合计 × 10%)
预计总费用 = 交通 + 住宿 + 餐饮 + 门票 + 其他
```

校验：

- 交通必须覆盖所有人和所有去返程。
- 房间数按成人/儿童规则计算。
- 各项与总预计费用必须相等。
- 用户预算上限只作为约束，不要求刚好花完。

### G. 逐日文案生成

在时间轴和预算通过后，按天依次调用 DeepSeek。

每日输入只包含：

- 当天的已校验时间轴。
- 当天使用的候选景点。
- 当天天气。
- 当天预算分项。
- 用户兴趣与节奏。

每日输出：

```ts
type DayCopy = {
  day: number;
  purpose: string;
  highlights: string[];
  cautions: string[];
  history: { source: string; content: string }[];
};
```

### H. 单日文案校验

每日文案生成后立即校验：

- day 必须与请求一致。
- 景点名称必须来自当天候选。
- 摘要不得提到当天未安排的景点。
- 历史引用必须有来源，无来源直接丢弃。
- 文案不得覆盖本地时间、价格和人数。

通过后才进入下一天，也才允许渲染并推送该日页面。

### I. 逐页推送

页面顺序仍保持：

```text
封面、概览、路线、预算
+ 每天两页
+ 来源、回望、结束页
```

页面流式规则：

- 固定高度预览，内部滚动，不让外层文档高度不断变化。
- 单页只在本页依赖的校验通过后推送。
- 用户滚动后不得自动把页面拉回顶部。
- 全部页面通过后才允许导出 PDF。

## 6. 失败策略

- 交通模式失败：回退用户显式选择或停留在上一阶段，不生成游玩计划。
- 交通门到门时长超出每日窗口：不允许截断后继续，timeline 阶段 fail closed 并明确提示。
- POI 候选不足：停止并明确提示“候选景点不足”。
- DeepSeek 提案不合法：最多修复当前提案一次，仍失败则降级为移动日/休息日，不污染预算。
- Tavily 价格缺失：使用本地最低参考价并标注“参考价”。
- 单日文案失败：该页显示“本页分析未能生成”，继续生成其余日期。
- 当日容量不足：优先减少或跳过晚餐、休息，仍先安排可容纳的短景点；确实低于最小景点容量时只降级当天为周边活动/休整，不阻断其余天数。
- 预算不平：不允许导出 PDF，先修正计算；确定性预算按整数分摊到对应每日节点，余数进入最后一个分配节点，每日合计必须等于预算总额。

## 7. 测试与验收

必须包含：

- 1963 km 北京到四川默认飞机，5 人往返运输按人数累加。
- 5 人 5 天住宿按房间数 × 晚数计算。
- 通勤时长从每日容量扣除。
- 非移动日必须包含真实候选景点。
- 逐日文案失败不阻塞其他日期。
- 候选景点不足时不出废稿。
- 地图起终点完整可见，缩放不裁切。
- 预览容器固定高度，不自动跳页，无双滚动条。
- PDF 与页面使用同一份通过校验的数据。

## 8. 阶段顺序与失败/降级矩阵

实现与文档统一使用以下顺序，不允许跳过前序阶段：

```text
route -> pois -> selection -> timeline -> prices -> budget -> narrative -> pages
```

| 阶段 | 主要事实来源 | 通过后产物 | 失败或降级策略 |
| --- | --- | --- | --- |
| `route` | 高德坐标/距离 + 本地交通规则 | 每个 leg 的方式、距离、门到门分钟数和单人最低价 | 缺少端点、距离或有效交通方式时 fail closed，不进入 POI 和预算阶段 |
| `pois` | 高德 POI 搜索与过滤 | 已去重、带坐标和公开 URL 的候选景点 | 优先使用明确标记的本地 seed 降级；仍不足时停止游玩日生成，不允许模型虚构景点 |
| `selection` | DeepSeek 在候选 ID 内选择 | `day/candidateId/sequence/stayMinutes/reason` | 非法候选 ID 最多原地修复一次；仍失败则终止，不启动 timeline 或 budget |
| `timeline` | 本地容量与固定节点计算 | 不重叠、不越界的每日执行时间轴 | 先扣交通、换乘、用餐、入住和必要休息；单日容量不足时改为附近短景点、周边活动或休息 |
| `prices` | Tavily 资料 + 本地最低价 | 交通与门票的区间、来源和置信度 | Tavily 缺失或超时标记为 `reference` 或 `fallback`；不得据此伪造 `verified` |
| `budget` | 本地算术 | 交通、住宿、餐饮、门票、其他和预计总计 | 任一项不平或覆盖所有人/leg/晚数时失败，禁止导出 PDF |
| `narrative` | DeepSeek 基于已冻结排程生成 | 单日主题、目的、重点、提醒和带来源历史 | 单日失败只替换为经过校验的本地安全文案，继续生成其他日期 |
| `pages` | 已通过校验的日文案与模板 | 带 `runId`、连续 `index`、`checksum` 的页面事件 | checksum、index 或 run 校验失败时停止该页面消费；全部页面通过前不得导出 |

`PlanningRun` 只允许目标阶段从 `pending` 进入 `running`，前序状态必须是 `passed` 或 `degraded`。当前独立落地的确定性模块包括状态机、交通规划、时间轴、预算、候选过滤、逐日文案校验和页面协议；完整生产阶段处理器的接线以 Golden E2E 通过为验收门槛。

## 9. API 职责边界

| 系统 | 可以负责 | 不可以负责 |
| --- | --- | --- |
| 高德 | 路线、坐标、POI、距离、驾车时长、导航链接 | 虚构班次、票价或景点预约状态 |
| 本地确定性模块 | 交通方式、门到门时间、每日容量、房间数、人数乘算、预算算术、校验与降级 | 生成没有候选依据的景点文案 |
| Tavily | 非自驾交通价格资料、景点门票与优惠资料 | 直接决定最终时间轴或总预算 |
| DeepSeek | 从候选景点中选择、排序、分析和写文案 | 修改价格、人数、通勤时间、每日容量或最终总价 |

DeepSeek 的选择输出必须包含候选 ID；如果后续接线遗漏候选校验，应视为阶段失败，而不是把模型自由文本直接交给时间轴。

## 10. 价格来源与置信度

预算计算口径如下：

```text
交通 = 单人单程价格 × 人数 × leg 数
住宿 = 房间数 × 晚数 × 每晚价格
餐饮 = 人数 × 天数 × 每人每日餐标
门票 = 成人人数 × 成人票价 + 儿童人数 × 儿童票价（或统一票价 × 总人数）
其他 = max(200, 前四项合计 × 10%)
预计总费用 = 交通 + 住宿 + 餐饮 + 门票 + 其他
```

每一笔价格都必须保留来源和置信度：

- `verified`：有明确来源、日期和适用范围，可作为已核验参考价。
- `reference`：来自检索资料，但班次、淡旺季或库存可能变化，只能作为参考区间。
- `fallback`：来自本地最低价、公式或安全兜底；界面必须显示为参考价，不能伪装成实时报价。

用户预算上限只用于校验方案是否超出条件，不要求把预算刚好花完；若总预计费用无法由分项加总得到，应阻断导出。

## 11. 缓存、run 与幂等

- `PlanningRun` 是阶段状态与错误边界，不是长期数据存储。每次规划使用独立 `runId`，阶段缓存键必须包含阶段输入、规则版本和必要的模型/数据版本，不能只按目的地复用。
- 当前已实现单日文案缓存：键由标题、日期、天气、节奏、人数、兴趣和最终节点生成 SHA-256；同一天排程未变时，预览和 PDF 可复用文案，最多保留 300 条。
- 阶段级持久化缓存尚未作为已实现能力；如后续启用，必须在每次复用前重新执行该阶段的校验，不得直接信任缓存状态。
- 页面事件顺序为从 0 连续的 `index`，内容校验使用 SHA-256 `checksum`。客户端只接受当前 `runId`，拒绝旧 run、乱序和重复 checksum，并在计划 key 变化时中止旧 fetch。

## 12. 预览、PDF 与超时兜底

- 预览和 PDF 共用 `prepareGuidebookDayNarrative` / `prepareGuidebookNarrativePlan` 的校验与 fallback 规则；通过校验的每日文案才允许固化到页面。管家计划不会在导出时被 legacy enrichment 二次改写。
- 页面对地图、导航和历史来源做安全校验；PDF 超时返回安全可打印 HTML，移除地图、导航和历史引用，并重新校验每日文案。
- PDF 总超时默认 25 秒；超时后使用 AbortSignal 停止文案准备和渲染，避免后台继续消耗模型或浏览器资源。

## 13. 上线与回退

- `BUTLER_PLANNER=1` 或未设置：默认启用管家/确定性路径。缺少 `DEEPSEEK_API_KEY` 或高德 Key，或 route/POI/交通等硬前置阶段失败时 fail closed；Tavily 缺失只降低价格置信度。
- `BUTLER_PLANNER=0`：显式切换回 legacy 路径，仅用于故障对照或回退。
- 确定性模式失败时结果页只显示错误或配置提示，不挂载本地兜底路书，也不提供 PDF 导出。
- 上线顺序：独立模块测试 -> 分阶段校验测试 -> 北京到四川 Golden E2E -> 预览与 PDF 同源验证 -> 默认路径。事故或结果异常时可通过 `BUTLER_PLANNER=0` 临时回退，但不能让过期 run 继续覆盖当前预览。

## 14. 用户验收清单

- 北京到四川、5 人、5 天往返默认显示飞机，交通费用按 5 人和往返 leg 累加，住宿按房间数 × 晚数。
- 通勤时间已从每日容量扣除，非移动日包含真实候选景点，不连续出现“自由休整/自由活动”。
- 路线地图完整显示起点和终点，缩放不裁切；每日地图也显示当天起终点。
- 路书预览固定高度、内部滚动、无双滚动条、不自动跳页，且进度逐页推进。
- 预览与 PDF 的预算、日期、人数、交通方式、每日文案和降级结果一致；PDF 失败或超时时能输出安全可打印 HTML。
